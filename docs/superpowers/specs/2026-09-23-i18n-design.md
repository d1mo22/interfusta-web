# i18n: ca (default) + es / fr / en / pt

## Context
The public site is Catalan-only (`<html lang="ca">`, hardcoded strings in ~12–14 files, project content in Neon). We want the site in 5 languages so tourists and foreign clients can read it. UI text comes from per-language message files; project content in the DB is auto-translated with Azure Translator on save and can be reviewed/overridden in the admin. The admin panel itself stays Catalan.

### Decisions (agreed)
- Locales: `ca` (default + fallback), `es`, `fr`, `en`, `pt`.
- URLs: Catalan unprefixed (`/portfolio`), others prefixed (`/fr/portfolio`). Existing URLs keep working.
- Detection: first visit to an unprefixed URL uses `Accept-Language`, result stored in a `NEXT_LOCALE` cookie; after that the cookie wins. The switcher sets the cookie.
- DB: one `translations jsonb` column per table. Catalan stays in the existing columns.
- Translator: Azure Translator F0 (2M chars/mo free, checked on the official pricing and language pages on 2026-09-23), called with plain `fetch`, no SDK. We dropped DeepL because its API Free plan can't be bought since July 2026. Only the Developer plan (1M characters one-time) and the paid Growth plan remain.
- Admin: saving auto-translates; the project edit page gets a "Traduccions" tab to review or override the text.
- No i18n library. Use the Next 16 built-in pattern from `node_modules/next/dist/docs/01-app/02-guides/internationalization.md` (`[lang]` segment, `getDictionary`, `next/root-params`).

## 1. Static UI text
- `messages/{ca,es,fr,en,pt}.json` with nested keys (`nav.portfolio`, `home.hero.title`, `contact.errors.name`, ...).
- `lib/i18n.ts`: `locales`, `defaultLocale`, `hasLocale()`, `getDictionary()` (reads `lang()` from `next/root-params`), `localeHref(lang, path)` (no prefix for `ca`).
  - Type the dictionaries map as `() => Promise<typeof ca>`. `tsc` then fails if any language file is missing a key, so no separate checker script is needed.
- Server components call `getDictionary()`. Client components (home, contact, portfolio clients, navigation) receive their `dict` slice as a prop from a server wrapper.
  - The home `page.tsx` is fully client-side today. Split it into a server `page.tsx` and a `client-home.tsx`.
- `data/featured-project.json` text moves into the message files.
- `formatDate` in `lib/utils.ts:7` takes a locale instead of the hardcoded `"es-ES"`.
- The backfill script (§4) creates the first draft of the 4 non-Catalan files. You review them.

## 2. Routing
- Move `app/(site)/**` to `app/[lang]/(site)/**`. `app/[lang]/layout.tsx` becomes the root layout for the site:
  - `<html lang={lang}>`, `generateStaticParams` over the locales, and `notFound()` for unknown locales.
- `app/(admin)/layout.tsx` becomes its own root layout with `<html lang="ca">`. `app/layout.tsx` is removed; shared fonts and metadata move into both layouts.
- `not-found` and `global-error` need to be re-checked against the Next 16 multiple-root-layouts docs during implementation.
- `generateMetadata` on the site pages: translated title/description plus `alternates.languages` hreflang links for the 5 URLs.
- `proxy.ts`: widen the matcher to everything except `_next`, static assets and `/api`. Keep the existing auth branch for `/admin` and `/api` unchanged. For site paths:
  - `/ca/...` → redirect to the unprefixed URL.
  - `/{es,fr,en,pt}/...` → pass through.
  - Unprefixed:
    - Cookie set to a non-`ca` locale → redirect to that locale's prefix.
    - No cookie → match `Accept-Language` (a small hand-written parser, no `negotiator` dependency), set the cookie, and redirect if the match isn't `ca`.
    - Otherwise → **rewrite** to `/ca/...`.
  - Put the decision in a pure `resolveLocale(pathname, cookie, acceptLanguage)` function so it can be tested.
- Language switcher in `components/navigation.tsx`: sets the `NEXT_LOCALE` cookie, then navigates to the same path in the chosen locale.
- Every internal site link goes through `localeHref`.

## 3. DB content
Migration. The repo has no migrations folder, so add `db/migrations/001_i18n.sql` and run it against Neon manually:
```sql
ALTER TABLE project  ADD COLUMN translations jsonb NOT NULL DEFAULT '{}';
ALTER TABLE feature  ADD COLUMN translations jsonb NOT NULL DEFAULT '{}';
ALTER TABLE category ADD COLUMN translations jsonb NOT NULL DEFAULT '{}';
```
- The shape is `{"es": {"title": "...", "description": "...", "full_description": "...", "duration": "..."}, "fr": {...}}`. `feature` and `category` store a single key: `description` or `name`.
- Reads in `app/actions/data.ts` (`getPortfolioData`, `getProjectDetails`) take an optional `lang` (default `ca`, which the admin uses) and select `COALESCE(p.translations->${lang}->>'title', p.title)` and so on. Missing translations fall back to Catalan. For `ca` the path is unchanged.
- `image.alt_text` is not translated. It's built from the translated title at render time.
- The `'Todos los Proyectos'` filter in `getCategories` stays as-is. It filters by the Catalan column.

## 4. Machine translation (Azure Translator)
- `lib/translate.ts`: `translateTexts(texts: string[])` makes **one** POST to `https://api.cognitive.microsofttranslator.com/translate?api-version=3.0&from=ca&to=es&to=fr&to=en&to=pt-pt`. Azure takes several `to` targets in a single call, so all 4 languages come back at once. `pt-pt` is the Portugal variant, the likely audience in Andorra; plain `pt` would give Brazilian Portuguese.
  - Headers: `Ocp-Apim-Subscription-Key` and `Ocp-Apim-Subscription-Region`, read from the `AZURE_TRANSLATOR_KEY` and `AZURE_TRANSLATOR_REGION` env vars. Both also have to be added in Vercel.
  - Keep the function behind that one-function interface so another provider can replace it later without touching the callers.
- `createProject` / `updateProject` (`app/actions/project.ts`):
  - Only translate Catalan fields that changed compared with the stored row. A create counts as all fields changed.
  - Unchanged fields keep their existing translations, which preserves manual overrides.
  - Features are deleted and reinserted on update, so a new feature row whose Catalan text matches an old one reuses that old row's translations.
- Categories (`app/actions/categories.ts`): same rule for `name`.
- **Failure:** if the translation call errors (including the free-tier quota being used up; don't retry that) or times out, the Catalan text still saves (log the error) and translations are left missing. The site falls back to Catalan. The admin shows a "Traducció pendent" badge and a "Retradueix" button (a server action that re-runs the translation for that project).
- `scripts/translate-backfill.ts`: a one-off run that translates every existing project, feature and category, then drafts `messages/{es,fr,en,pt}.json` from `ca.json`. It never overwrites keys that already exist.
- `revalidate()` in `project.ts` switches to `revalidatePath('/', 'layout')`. The site is small, so revalidating all locales at once is fine.

## 5. Admin "Traduccions" tab
- On `app/(admin)/admin/projects/[id]/edit`: a tab with language sub-tabs (es/fr/en/pt), each showing editable title, description, full_description, duration and features, prefilled from `translations`.
- Saving calls a new `updateProjectTranslations(id, translations)` action. It writes the jsonb directly, with no translation call.
- The existing wizard steps are unchanged.
- Categories: auto-translate only, no manual override UI. Add one if a bad translation shows up.

## Out of scope
- Translating the admin UI and the contact email sent to the business (stays Catalan).
- A sitemap. None exists today; hreflang metadata covers SEO for now.

## Verification
- `npx next typegen && npx tsc --noEmit`: catches missing message keys.
- `node --experimental-strip-types lib/i18n-config.check.ts` and `lib/translate.check.ts`: assert-based checks of `resolveLocale` and the translation merge rules (prefix, cookie, Accept-Language, `/ca` redirect).
- `npm run build`: all 5 locales prerender.
- Manual run with `npm run dev`:
  - `/` with `Accept-Language: fr` and no cookie → redirects to `/fr`. With a `ca` cookie → stays on `/`.
  - `/fr/portfolio/1` shows French content. A project with no translations shows Catalan.
  - `/admin` still requires login, and `/api/upload` POST still returns 401 without a session.
  - Edit a project's Catalan title in the admin → the French title updates. Edit only the French title in Traduccions → a later save that leaves the Catalan unchanged keeps it.
  - With `AZURE_TRANSLATOR_KEY` unset → the save still succeeds and the "Traducció pendent" badge shows.
- The migration needs testing on a Neon branch before prod (same as for the redesign PR).
